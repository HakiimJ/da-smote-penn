# The limits of protected editing in hybrid resampling: A rigorous empirical analysis of density-aware oversampling under class overlap

[![Status: Under Review](https://img.shields.io/badge/Status-Under_Review-blue.svg)]()

This repository contains the data and computational code necessary to fully replicate the analyses, simulations, and benchmarking tables presented in the working manuscript: **"The limits of protected editing in hybrid resampling: A rigorous empirical analysis of density-aware oversampling under class overlap"** by Ahmad Hakiim Jamaluddin and Nur Zafnazuhani Jailani.

*Note: A permanent DOI will be minted via Zenodo upon the formal acceptance and publication of the manuscript.*

## Overview

Hybrid resampling methods attempt to address class imbalance and class overlap simultaneously by combining minority oversampling with post-generation cleaning. A plausible assumption in this literature is that original minority boundary points should be protected during the cleaning stage to avoid the erosion of rare but informative samples. 

This project investigates that assumption by evaluating **DA-SMOTE-PENN**—a two-stage pipeline combining density-aware oversampling with minority-protective Edited Nearest Neighbours (ENN). Using a rigorous protocol involving full-dimensional real-world datasets and controlled simulation regimes, the codebase tests whether aggressive boundary preservation is beneficial, or if it counterproductively retains ambiguous, noisy instances when minority support is sparse.

The codebase evaluates a comprehensive suite of methods and classifiers:
* **Resampling Baselines:** SMOTE, ADASYN, Borderline-SMOTE, SMOTE-Tomek, SMOTE-ENN, LD-SMOTE.
* **Ablation Variants:** DA-SMOTE (Oversampling only), PENN (Editing only).
* **Classifiers Evaluated:** $k$-Nearest Neighbours ($k$-NN), Logistic Regression, Radial-Basis-Function SVM (RBF-SVM), Random Forest, and XGBoost.

## Repository Structure

The pipeline is fully automated and will dynamically generate the following directories upon execution:

* `benchmark.R`: The master execution script containing the full pipeline for data preparation, hyperparameter tuning, model training, cross-validation, and statistical testing.
* `data/`: Automatically populated with the 8 real-world benchmark datasets (via `modeldata`, `ROSE`, and `mlbench`) exported as CSVs.
* `outputs/results/`: Contains all generated raw outputs, including fold-level metrics, hyperparameter logs, simulation results, ablation/sensitivity summaries, and non-parametric statistical test results (Friedman/Holm).
* `outputs/tables/`: Contains the publication-ready `.tex` table files dynamically generated by the script, matching the manuscript formatting perfectly.

## System Requirements and Dependencies

All analyses, simulations, and statistical tests were programmed and executed in the **R statistical computing environment**. 

To run the master replication script, ensure you have the following R packages installed. The script includes a module to automatically install missing dependencies from CRAN.

**Machine Learning & Classifiers:**
* `FNN`, `class` ($k$-NN)
* `e1071` (SVM)
* `ranger` (Random Forest)
* `xgboost` (XGBoost)

**Resampling & Evaluation:**
* `pROC`, `PRROC` (AUROC and AUPRC metrics)
* `coin` (Statistical testing)
* `ROSE`, `mlbench`, `modeldata` (Benchmark datasets)

**Data Wrangling & Pipeline Iteration:**
* `dplyr`, `tidyr`, `purrr`, `stringr`, `tibble`, `data.table`
* `rsample` (Cross-validation folding)

## Usage: Replicating the Analysis

To replicate the findings, tables, and statistical tests from the paper:

1. Clone this repository to your local machine:
```bash
git clone [https://github.com/YOUR_USERNAME/da-smote-penn.git](https://github.com/YOUR_USERNAME/da-smote-penn.git)
cd da-smote-penn

```

2. Execute the master benchmark script. You can run this interactively in RStudio, or via the command line:

```bash
Rscript benchmark.R

```

*Note: The full benchmark performs nested cross-validation across multiple classifiers, datasets, and oversampling grids. Execution may take several hours depending on available CPU threads.
